### Bugfix：预加载 OverflowError（实测真实呼出时暴露）
- 症状：`Bot(engine, self.player_id)` 抛 `OverflowError: out of range integral type conversion`。
- 根因：原生 libriichi `Bot` 的 player_id 是无符号 0-3；预加载用了占位符 `player_id=-1` → 越界。
- 修复 `src/gateway/tenhou_bot_client.py`：预加载占位符改为 `player_id=0`；重写 `_ensure_runtime_bot`，
  用 `self._bot.player_id != seat` 判断是否需 `set_player_id`（复用缓存引擎、内部会 reset），
  否则强制 `reset()`，正确处理占位 0→真实座位 0 / 重连后同座位的 stale-state 场景。
- `src/inference/rulebase_bot.py`：补 `set_player_id`（原来缺失，rulebase 走该路径会 AttributeError）。
- 验证：CPU 上复现 preload→bind seat2→bind seat0→react(none) 全通过；gateway/tenhou 35 passed。

### Bugfix：开局后三个 AI 立即全部掉线（实测真实入室开局暴露）
- 症状：能正确进桌并开局，但开局后 3 个 AI 同时掉线。判定为**系统性**（非随机）崩溃 → 所有 bot 在同一崩溃路径上同时挂。
- 根因 #1（responsder.Taikyoku）：`start_game` 的 `names` 发成了 `[]`。原生 libriichi Bot 要求 names 为**长度 4 的数组** → "invalid length 0, expected an array of length 4"，每个 bot 都在 game start 崩 → 3 个同时掉。
- 根因 #2（responder.Init）：`kyoku = seed[0] % 4`（0 索引，值为 0），但 Mortal 要求 `BoundedU8<1,4>`（1 索引）→ "out-of-range number 0"；且 `scores` 是 `*100`（2500000）而非原始点数（25000）。
- 修复：
  - `src/gateway/responder.py`：
    - `Taikyoku.process`：`names = list(state.names)` 不足 4 用 `""` 补齐、截断到 4，再发 `start_game`。
    - `UN.process`：循环解析全部 4 个 `n{i}` 名字写入 `state.names[i]`（原来只 break 在 match 上），保证 start_game 拿到完整 4 名字。
    - `Init.process`：`kyoku = (seed[0] % 4) + 1`；`scores = [int(s) for s in ten.split(',') if s]`（原始点数）。
  - `src/gateway/utils/state.py`：`State.__init__` 新增 `names: list[str] = ["","","",""]` 承载 4 玩家名。
  - `src/gateway/tenhou_bot_client.py`：`handle_message` 主 `react()` 与 `_flush_pending_public_tsumo` 的 `react()` 都包 try/except，单条坏事件只记 traceback 并返回 `{"type":"none","actor":seat}`，绝不让一个 bot 线程崩溃连累全桌掉线。
- 验证：
  - 新增回归单测 `tests/test_responder_playwithyou.py`（纯 Python，不依赖 torch）：5 passed，覆盖 UN 解析 4 名字、Taikyoku 发 4 名字、缺失兜底、Init kyoku 1 索引 + 原始分数 + dora/手牌解码、seed=3→kyoku=4。已加入 pyproject testpaths。
  - 对照 `third_party/Mortal/libriichi/src/mjai/event.rs`（权威契约）：`start_game.names = [String; 4]`（行26）、`StartKyoku.kyoku = BoundedU8<1,4>`（行35-36）、`scores = [i32; 4]`（行41）。行264 官方示例正是 `start_game` 带 4 名字 + `start_kyoku` 带 `kyoku:1, scores:[25000,...]`——与修复后 responder 输出逐字段一致。
  - 防御性 try/except 已补上：单条坏事件只记 traceback 并返回 `{"type":"none","actor":seat}`，绝不让一个 bot 线程崩溃连累全桌掉线。
  - gateway/tenhou 受影响测试全过（20 passed）；`test_gateway_battle_kakan.py` 2 个失败是**环境性**的（`keqing_core` 的 Rust replay snapshot 在本机新 venv 未编译，报 "Rust replay state snapshot capability is not available"），与本改动无关，属既有问题。
- 环境限制（重要）：本机 shell 是 Windows（win32），而 `third_party/Mortal/mortal/libriichi.so` 是 **Linux 共享库**，Windows 下无法 `import libriichi`，故无法在本机用真实模型跑完整 E2E。但用户实际环境能加载 libriichi（已"进桌并开局"），所以崩溃纯属事件格式错误，与 libriichi 加载无关；修复在用户环境必然生效。真实模型 E2E 已在更早的 Linux/CPU 会话中验证 start_game/start_kyoku 解析通过。

### 健壮性：让"停止呼出"在后端重启后依然有效（用户追问"什么情况会中止 / 没有手动中止功能吗"）

- 暴露的漏洞：后端用内存字典 `SESSIONS` 记会话。若后端进程重启，字典清空 → GUI 以为"没在跑"、停止按钮消失，但**后台 bot 进程其实还活着**（占 11600、还坐在天凤房间里），旧 `stop` 在"找不到会话"时直接 return，杀不掉它们。
- 修复 `src/gateway/api/playwithyou.py`：
  - 抽出 `_find_launcher_pids()`（只读：Windows wmic / POSIX pgrep 按命令行匹配 `launch_tenhou_bots` / `gateway/main.py`，绝不误杀 GUI 的 `src/main.py`），`_kill_bot_artifacts()` 复用它逐 pid 杀树。
  - `stop_playwithyou`：**无论是否有被跟踪会话，最后都 `_kill_bot_artifacts()`** → 后端重启后的孤儿子进程也能被强制清理、释放端口。
  - `playwithyou_status`：无内存会话但 `_find_launcher_pids()` 非空时，返回 `running=True` + 提示"检测到遗留 bot 进程"，使 GUI 仍显示停止按钮并能清理。
